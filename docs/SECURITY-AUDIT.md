# Проверка безопасности Bebekon VPN — 5 октября 2026

Проверены исходники Windows и Android, границы привилегий, подписки и правила, TLS, хранение секретов, журналы, загрузка обновлений и зависимости. Найденные проблемы исправлены в Windows 0.1.19 / Android 0.1.6. Проверка не является сертификацией и не доказывает отсутствие неизвестных уязвимостей. Не проводились атаки на серверы провайдеров, пользовательские устройства или сторонние сервисы.

Исходная точка: `c89f92442727ae9c7414bace4081dec5b3b1aca1`, Windows 0.1.18, Android 0.1.5. Модель угроз включает постороннее Android-приложение, другого локального пользователя Windows, подменённую подписку, недоверенную сеть, вредоносный VPN-сервер и подменённый пакет обновления. Полный контроль администратора/root над устройством и кража ключей издателя рассматриваются как ограничения защиты клиента.

## Исправленные проблемы и возможные действия злоумышленника

Уровни ниже — оценка для нашего клиента с указанными условиями, а не CVSS upstream-библиотек.

Это могло отключить защиту или неожиданно включить туннель; ограничения фонового запуска Android влияют на доступность атаки. | Средний | MainActivity больше не принимает команды VPN. Передача согласия из Quick Settings идёт через отдельную неэкспортированную TileConnectActivity; сама служба плитки защищена системным разрешением. На Android 12+ включено системное скрытие сторонних overlay-окон над основным интерфейсом. Это дополнительная защита от некоторых атак с подменой нажатий; она не защищает от всех злоупотреблений Accessibility.

## Существующие границы защиты, которые проверены

- Windows IPC: только SID владельца установки и SYSTEM, запрет сетевых логонов, дополнительная проверка impersonated SID. Клиент сверяет PID сервера pipe с работающей зарегистрированной отдельной службой **до** передачи подписки. Служба принимает структурированную модель, сама генерирует конфигурацию; не принимает произвольную команду, путь executable или сырой конфиг. Фреймы ограничены 4 МиБ и временем чтения. Живой тест отвергает pipe от незарегистрированного процесса. Отдельный Windows logon другого пользователя не создавался; проверка межпользовательской границы основана на коде ACL/SID и тестах идентичности.
- Исполняемые файлы службы имеют фиксированные пути, аргументы передаются без shell. Дочерние ядра помещаются в kill-on-close job. Настройки и mirror соединения зашифрованы Windows DPAPI CurrentUser; сериализованный временный буфер очищается после шифрования. Конфиги службы доступны SYSTEM/Administrators и удаляются при остановке.
- Локальные bridges/probes используют loopback и случайные пароли. Windows API статистики имеет новый случайный bearer secret на каждую сессию; наружу/в IPC передаются агрегированные счётчики. Веб-панель ядра не публикуется в LAN.
- Android использует внутреннее хранилище и Android Keystore, отключает backup. VPN-service и Quick Settings защищены системными signature-разрешениями, FileProvider не экспортирован и ограничен папкой обновлений. Launcher остаётся экспортированным для запуска и предложения импорта; импорт требует действия пользователя и не исполняет поля провайдерского конфига.
- Windows update.json проверяется встроенным RSA-3072 ключом; подпись связывает версию, URL, размер и SHA-256. Подменённые подписи, пакеты, старые версии, небезопасные адреса и пути отклоняются. Пакет повторно проверяется и удерживается read-only при запуске; повышение прав проходит через UAC.
- Android обновляется только с разрешённых GitHub HTTPS-адресов. Проверяются digest, размер, applicationId, более новый versionCode, версия и соответствие сертификата установленному приложению. Системный установщик дополнительно проверяет подпись APK и сохраняет пользовательское подтверждение. Ключи подписи обеих платформ не находятся в репозитории/пакетах и не менялись.
- В режиме IPv4 Android системная конфигурация, DNS и ядро согласованы; ранее добавленная регрессия проверяет A/AAAA и блокирование литерального IPv6 из отдельного UID. Это не доказательство отсутствия утечек при любом устройстве, смене сети или аварии.

## Зависимости и проверка известных уязвимостей

1. `dotnet list Bebekon.sln package --vulnerable --include-transitive --format json`: известных уязвимых NuGet-зависимостей не сообщено.
   Встроенный runtime проверен отдельно: Windows использовал 10.0.8. SDK обновлён до 10.0.401, runtime и системные NuGet-библиотеки — до 10.0.12. [Microsoft перечисляет накопительные исправления безопасности .NET 10](https://github.com/dotnet/core/blob/main/release-notes/10.0/cve.md); совпадение версии не доказывает достижимость каждого CVE в нашем приложении. Загрузка SDK проверена по SHA-512 официального release metadata; установка сделана локально для сборки, без замены глобальных SDK пользователя.
2. OSV querybatch по 97 разрешённым пакетам Android releaseRuntimeClasspath: известных затронутых Maven-пакетов не сообщено. Передавались только координаты пакетов, без исходников, ключей и подписок. Воспроизведение: сохранить вывод Gradle `:app:dependencies --configuration releaseRuntimeClasspath`, затем запустить `scripts/audit-maven.py input.txt output.json`.
3. `govulncheck` 1.8.0: исходные готовые Windows sing-box/Xray дали соответственно 16 и 56 предупреждений. **Это не число доказанных эксплуатируемых уязвимостей клиента**: сканер stripped-бинарника может использовать модульные совпадения без точной достижимости. Оба ядра пересобраны с Go 1.26.8 и исправленными версиями grpc, x/crypto, x/net, x/mod, chi, go-jose, compress и dhcp. Состав закреплён в `core/security-pins.json`; сборка воспроизводится `scripts/build-secure-cores.ps1` и `android/build-core.ps1`.
4. Финальные source/callgraph scans Windows sing-box, Xray и Android libbox: **0 предупреждений в вызываемых функциях, 0 в импортированных пакетах**. Остаётся одно модульное предупреждение [GO-2026-5932 — неподдерживаемый OpenPGP](https://pkg.go.dev/vuln/GO-2026-5932): модуль присутствует в графе, но соответствующие пакеты не импортируются нашими сборками. Binary scans двух Windows файлов и трёх Android ABI также отдельно проверены; их модульное предупреждение не скрывалось. См. [принцип работы govulncheck](https://pkg.go.dev/golang.org/x/vuln/cmd/govulncheck).
5. Отдельно разобрана [TLS advisory Xray GHSA-5wf9-h793-w73c](https://github.com/XTLS/Xray-core/security/advisories/GHSA-5wf9-h793-w73c). Она относится к gRPC/Hysteria2 с pinningCA и незаданным serverName. Наш Xray используется только для XHTTP, а генератор задаёт serverName; этот сценарий через наши конфигурации недоступен. Это **не** заявление, что старый upstream Xray целиком получил соответствующий source fix.
6. Gitleaks 8.30.1 проверил историю из 28 коммитов (12,38 МБ). Одно срабатывание — поле private_key в скопированном upstream TLS-примере документации; строка совпадает с публичным примером sing-box. Реальные ключи подписи и предоставленные пользователем секретные URL среди tracked-файлов не обнаружены. Значения секретов не включались в отчёт.

Базы уязвимостей меняются; приведённые результаты действительны для даты проверки. Новый security pin требует повторных проверок конфигураций, протоколов и трафика, а не только успешной компиляции.

### Оставшийся риск TrustTunnel

Windows TrustTunnel Client 1.1.7 сохранён из официального релиза с проверенным SHA-256. [Опубликованных advisories самого клиента на дату проверки нет](https://github.com/TrustTunnel/TrustTunnelClient/security/advisories), что не доказывает его безопасность.

Его source recipe ссылается на AdGuard nghttp2 1.56.0. [Vendor recipe](https://github.com/AdguardTeam/NativeLibsCommon/blob/v8.1.52/conan/recipes/nghttp2-1.56.0/conanfile.py) и семь доступных патчей просмотрены. У upstream nghttp2 есть [CONTINUATION CPU DoS, исправленный в 1.61.0](https://github.com/nghttp2/nghttp2/security/advisories/GHSA-x6x3-gv8h-m57q), и [условный assertion DoS, исправленный в 1.68.1](https://github.com/nghttp2/nghttp2/security/advisories/GHSA-6933-cjhr-5qg6). В просмотренных vendor-патчах соответствующие исправления не подтверждены. Нельзя по одному номеру версии доказать состав официального бинарника или достижимость каждого сценария.

**Открытая задача:** получить точный SBOM/подтверждение исправлений производителя либо собрать и проверить C++-ядро с исправленным nghttp2. До этого нельзя заявлять «все известные проблемы всех ядер устранены». Для недоверенного HTTP/2 TrustTunnel endpoint остаётся риск отказа/нагрузки; подтверждённого RCE в этой проверке нет. TLS-проверка сертификатов обязательна. TrustTunnel на Android пока не поддерживается.

## Проверки исправлений

- Windows: финальный полный набор с .NET 10.0.12 — 261 passed, 1 skipped (262 total), 0 ошибок/предупреждений сборки. Включены 11 security-тестов, отказ для user-owned runtime storage и реальные native protocol/helper/traffic проверки. Пропущен тест внешнего TrustTunnel endpoint, требующий отдельной тестовой учётной записи.
- PowerShell: реальные временные папки/ACL и junction проверены в `tests/security-helper-paths.ps1`: обычный путь принимается, junction в предке, выход за границу и файлы с недоверенным владельцем отвергаются. Рабочая установка пользователя не менялась.
- Android: 58 JVM-тестов прошли, Release Lint — 0 errors, 18 advisory warnings. Проверены сложные JSON/YAML, старый unsafe TLS, plugin file access, budgets, update validation и маршрутизация. Последние настройки версии не меняют эти проверки.
- Тест из отдельного Android UID прошёл: система отвергла внешний запуск private TileConnectActivity, а старый extra экспортированной MainActivity не смог включить выключенный VPN или отключить работающий. Подключение между двумя попытками было настоящим, через изолированный VLESS fixture. Общий API 35 прогон — OK (10 tests), 166,143 секунды, с двумя необязательными методами без внешних fixture. Подписанная 0.1.6 установилась поверх 0.1.5 и сохранила зашифрованную тестовую подписку/выбор. Подробности в [VALIDATION.md](VALIDATION.md); физический телефон не проверялся.

Локальные исходные отчёты находятся в `.tools/security/`, результаты тестов — в `artifacts/tests` и `android/app/build/validation`. Эти каталоги не публикуются целиком: в диагностике могут быть пути пользователя и служебные данные.

## Что клиент не может гарантировать

- Windows пока не имеет независимого firewall kill switch, сохраняющего запрет прямого трафика после аварии ядра. `strict_route` и DNS-защита не заменяют его. Android предлагает системный Always-on/«Блокировать соединения без VPN»; эта функция может конфликтовать с намеренно исключёнными Direct-приложениями.
- Первый Windows установщик не имеет Authenticode-сертификата издателя. RSA update feed защищает обновления уже доверенного клиента, но не первую загрузку с поддельного сайта. Используйте официальный GitHub release; SHA-256 рядом с файлом сам по себе не защищает от полного захвата того же аккаунта.
- Компрометация GitHub/машины издателя/ключа подписи может привести к вредоносному обновлению. Android certificate continuity и отдельный Windows RSA-ключ повышают порог атаки, но не защищают после кражи этих ключей. Нужны защищённые резервные копии и 2FA владельца; состояние внешнего аккаунта не менялось.
- Сервисы, намеренно направленные Direct, раскрывают обычный публичный IP. Режимы split tunneling не предназначены для сокрытия VPN от любого приложения. Провайдер VPN видит IP/время/объём соединения и часть метаданных; незашифрованный HTTP доступен выходному серверу. Некоторые поддерживаемые конфигурации допускают transport без внешнего TLS — провайдер и выбранный протокол должны быть доверенными.
- DPAPI/Keystore не защищают от malware с полным доступом в ту же учётную запись, root или администратора, чтения памяти процесса и злоупотребления разрешённой Accessibility-службой. Удаление всех копий секретов из памяти сборщика мусора не гарантируется.
- Полноценный C++ memory-safety аудит, fuzzing всех нативных протоколов, pentest инфраструктуры провайдеров, независимая лабораторная оценка и матрица всех Android OEM/версий/смен сетей не выполнены. На физическом телефоне пользователя исправления нужно проверить после обновления.

При подозрении на уязвимость сообщайте владельцу репозитория приватно, без действующей подписки, паролей или полного журнала в публичном issue. Перед публикацией нового релиза повторяйте сканирование зависимостей и проверки подписи.
