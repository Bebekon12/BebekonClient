# Проверка задержки, скорости и стабильности

Замеры проведены 18 ноября 2026 года на Windows. Маршруты и действующие VPN-подключения на компьютере во время проверки сохранялись. Версии кандидатов — Windows 0.1.28 и Android 0.1.13.

## Что удалось измерить

| Проверка | Результат |
| --- | --- |
| Полный HTTPS GET через текущую системную маршрутизацию до Google generate_204 | 10 из 10 ответов HTTP 204. Медиана времени до первого байта 209 мс, диапазон 180–351 мс |
| TCP-подключение к Cloudflare generate_204 с той же машины | 0 из 4 соединений за отведённые 4 секунды. DNS возвращал ответ |
| Скачивание с измерительного узла Cloudflare | 0 из 5 соединений за 5 секунд. Скорость для этого узла определить не удалось |
| HTTPS-загрузка с dl.google.com по текущим правилам | 5 из 5 ответов HTTP 206, по 2 МиБ каждый. Медиана 16,9 Мбит/с, диапазон 15,3–26,0 Мбит/с с установлением соединения |
| Локальный HTTP напрямую | 20 загрузок по 8 МиБ. Первый байт за 1,03 мс по медиане и 1,37 мс на 95-м процентиле. Медиана скорости 9 619 Мбит/с |
| Тот же локальный HTTP через sing-box и VLESS | 20 загрузок по 8 МиБ. Первый байт за 2,41 мс по медиане и 12,85 мс на 95-м процентиле. Медиана скорости 1 374 Мбит/с |

Локальный тест использует ядро из дистрибутива, два loopback-входа, один прогрев и чередование путей. Для воспроизведения выполните `python scripts/measure-local-routing.py core/sing-box.exe` из каталога проекта. Начальный DNS, TLS, удалённый сервер, MTU реального интерфейса и оператор связи в этом тесте не участвуют. Внешние замеры описывают текущий системный маршрут во время сборки и не изолируют конкретный выход Bebekon.

Во время проверки были запущены sing-box, служба Bebekon и NetBird. NetBird подтвердил management, signal и два подключённых узла. Счётчики ошибок и отброшенных пакетов Wi-Fi, Bebekon и wt0 показывали нули при чтении. Это один снимок. Для проверки обрыва при включении VPN требуется повторный запуск с теми же корпоративными маршрутами и DNS.

## Что влияет на показанный результат

Windows TCP измеряет три подключения до порта сервера и показывает медиану. HTTPS GET/HEAD проходит через выбранный VPN-сервер до проверочного сайта. На результат влияют DNS, установление транспортного соединения, TLS и ответ сайта. Windows по умолчанию использует Google, Android использует Cloudflare. Для сопоставления HTTPS-замеров на Android доступен Google в разделе «Серверы → Сайт для теста».

На Windows точная проверка каждого сервера запускает собственное ядро. При включённой геолокации неизвестной страны клиент также запрашивает страну выхода. Это занимает ресурсы и может задержать появление уже измеренного результата. В 0.1.28 массовая проверка стала ручной по умолчанию, а предел параллельных HTTPS-проверок снизился с шести до двух. На Android предел HTTPS-проверок снизился с четырёх до двух. Лёгкие TCP-проверки сохранили прежний лимит.

Проверка работоспособности при подключении Android пробует второй HTTPS-узел, если первый недоступен. Успешная контрольная точка должна вернуть HTTP 204. При ручной проверке используется выбранная точка, а приложение различает таймаут, HTTP-код и другие ошибки соединения. Это позволяет повторить замер с другим сайтом и сохранить смысл показанных миллисекунд.

## Что остаётся для сравнения с Happ и INCY

Для численного сравнения нужны одно устройство, одна сеть, один сервер подписки, одинаковые протокол, MTU, DNS, объём загрузки и проверочный URL. По очереди выполните на каждом клиенте серию холодных HTTPS-запросов и загрузок одного файла, фиксируя число ошибок, медиану и 95-й процентиль. Переключение Wi-Fi и мобильной сети проверяется отдельно с записью времени восстановления. В этой сессии сопоставимых замеров Happ/INCY и физического телефона не было. Причину всех наблюдавшихся ранее обрывов по этим данным установить нельзя.
